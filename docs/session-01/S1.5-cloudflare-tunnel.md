## Why a plan B

The plan was a free **Oracle Cloud Always Free** server, `navmarket-vps01`. I prepared:

- an Oracle Cloud account, home region **France Central (Paris)**, with two-factor authentication (MFA);
- a **dedicated SSH key** for this server (`ed25519`, private key in mode `600`, it never leaves my laptop);
- the network plan: new virtual network, public subnet, public IP, Ubuntu 26.04 **Minimal** image.

But the server could not be created: Oracle answered **"Out of capacity"** for both free server types, AMD (`E2.1.Micro`) and ARM (`A1.Flex`). The Paris region has only one data centre, and its free servers were all in use. Oracle's FAQ says this is temporary and advises trying again later.

Rather than waiting, I used the backup plan written in my roadmap: **publish my local server `navmarket-srv01` through a Cloudflare Tunnel**. The Oracle version of this lab will follow when servers are free again.

## How it works

```
Phone ──HTTPS──▶ Cloudflare ◀══ outgoing tunnel ══ cloudflared (navmarket-srv01) ──HTTP──▶ Nginx :80
```

- `cloudflared` runs on the server and opens an **outgoing** connection to Cloudflare, like a browser opening a website.
- Firewalls and home routers allow outgoing traffic by default, so **no port is opened** and the server needs **no public IP**.
- Visitors' requests reach Cloudflare, come back **through the tunnel**, and `cloudflared` forwards them to Nginx on `localhost:80`.
- Cloudflare provides the **HTTPS** certificate: the visitor gets a padlock without any certificate on my server.

A **Quick Tunnel** needs no Cloudflare account and no domain: it gives a random `*.trycloudflare.com` address.

## What I did

### 1. Install `cloudflared` from Cloudflare's package repository

```bash
sudo mkdir -p --mode=0755 /usr/share/keyrings
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg | sudo tee /usr/share/keyrings/cloudflare-main.gpg >/dev/null
echo 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main' \
  | sudo tee /etc/apt/sources.list.d/cloudflared.list
sudo apt update && sudo apt install cloudflared
cloudflared --version        # cloudflared version 2026.10.0
```

- The **signing key** lets apt check that every package really comes from Cloudflare; `signed-by=` uses this key for this repository only.
- A repository rather than a downloaded `.deb` file: `cloudflared` is then updated by every `apt upgrade`.
- `sudo tee` instead of `sudo echo … > file`: the `>` is done by my own shell **before** `sudo` runs, so it would be refused; `tee` runs with root rights and writes the file itself.

### 2. Start the Quick Tunnel

```bash
cloudflared tunnel --url http://localhost:80
```

`localhost` always means "this machine": Nginx listens on port 80 of the server itself. The command stays open and prints the public `https://<TUNNEL_URL>` address.

### 3. Test from my phone, then read the log

```bash
sudo tail -n 5 /var/log/nginx/access.log
```

## Reading the access log

| What I saw | Why |
| --- | --- |
| Client IP **`127.0.0.1`** | Nginx does not see the phone: it sees `cloudflared`, which runs on the same machine and connects to `localhost:80`. |
| **`200 196`** while the page is 233 bytes | The phone's browser asked for a **compressed** page, so Nginx sent fewer bytes. `curl` (S1.3) did not ask for it and got the full 233 bytes. |
| **`404`** on `favicon.ico` | Browsers ask for the site's small icon automatically; the storefront has none yet. |

## Why Nginx answered a name it does not know

The phone asked for `<TUNNEL_URL>`, while my site says `server_name navmarket-srv01;`. Nginx compares the requested name with each `server_name`; when nothing matches, it uses the **default server** for that port. With only one site enabled, `navmarket` **is** the default server, so it answers every name. ([How nginx processes a request](https://nginx.org/en/docs/http/request_processing.html))

## Why not this Quick Tunnel in production?

`cloudflared` itself is used in production by many companies. What is **not** made for production is the **Quick Tunnel**, the test mode I used here. Cloudflare presents it as a tool for testing and development.

| Quick Tunnel (this lab) | Production |
| --- | --- |
| Random address that changes at every start: customers cannot keep a link | **Named tunnel** linked to a Cloudflare account and my own domain: fixed address |
| Lives only while the command runs: `Ctrl+C` or a closed terminal = site offline | Runs as a **systemd service**: restarts after a failure, starts at boot |
| No account: no access control, no settings, no monitoring | Managed from the Cloudflare dashboard: access rules, logs, settings |
| Runs on my laptop's VM: if the laptop sleeps, the site is down | Runs on a server that is always on |

In short: the Quick Tunnel proves the idea in one command; production needs a **fixed address**, a **service that restarts by itself**, and **control** over who can access what.

## What I learned

- A cloud is made of real servers: "out of capacity" can happen, so I always need a plan B.
- One SSH key per use limits the damage if a key leaks; only the `.pub` file is shared.
- With SSH keys, my laptop **signs** a unique value with the private key, and the server checks it with the public key: the private key never travels.
- Adding a package repository safely: signing key + `signed-by`.
- An **outgoing tunnel** publishes a service without a public IP and without opening ports.
- Behind a tunnel, the server sees the tunnel's IP (`127.0.0.1`), not the visitor's.
- Nginx's default server answers when no `server_name` matches.
- Still to do: the same lab on Oracle Cloud (public IP, firewall rules), then a fixed tunnel or a real domain (lab S4.6).

## Quick questions

**Why does it work without opening any port?**
The server opens an outgoing connection to Cloudflare, and visitors' requests come back through it.

**Why not use this Quick Tunnel in production?**
Its address changes at every start and it stops with the command. Production needs a named tunnel with a fixed domain, running as a service.
