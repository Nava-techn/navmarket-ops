# S1.5 (Oracle) - NavMarket storefront live on Oracle Cloud

**Session 1 / 24 · Linux 1: using it** · Started on 22 October 2026 · In progress (proofs being collected)

## Goal

The server `navmarket-vps01` now exists on Oracle Cloud Always Free ([how I got it](S1.5-oracle-auto-launch.md)). Put the NavMarket storefront online **on this public server**, with its own public IP, and no tunnel this time ([plan B](S1.5-cloudflare-tunnel.md) is no longer needed).

**Done when:**

1. I can connect to `navmarket-vps01` over SSH with my dedicated key;
2. port 80 is open in **both** firewalls: Oracle's security list and iptables on the server;
3. Nginx serves the storefront from `/srv/navmarket`, with its own site configuration;
4. the storefront opens on a phone **on mobile data**, from outside my home network;
5. a new version can be deployed without visitors seeing a half-copied site, and rolled back in seconds.

## How a request travels

```
Phone (mobile data, anywhere)
   │  GET / HTTP/1.1  →  <PUBLIC_IP>, TCP port 80
   ▼
Oracle Cloud: Internet gateway of navmarket-vcn
   ▼
Firewall 1: security list of the public subnet      ingress rule: TCP 80 from 0.0.0.0/0
   ▼
navmarket-vps01 (VM.Standard.E2.1.Micro)
   ▼
Firewall 2: iptables INPUT chain                     ACCEPT tcp dpt:80, placed ABOVE the final REJECT
   ▼
Nginx (www-data)   server { listen 80; root /srv/navmarket; ... }
   ▼
/srv/navmarket/index.html  →  HTTP/1.1 200 OK
```

A packet must get through **both** firewalls. Opening port 80 in only one of them gives a page that never loads (timeout), not an error page.

## What I did

### 1. Connect over SSH

```bash
ssh -i ~/.ssh/navmarket_vps ubuntu@<PUBLIC_IP>
```

- `-i` picks the private key that matches the public key given to Oracle at creation.
- `ubuntu` is the default user of Oracle's Ubuntu images. It can use `sudo` without a password.
- The first time, SSH asks to confirm the server's fingerprint: it is saved in `~/.ssh/known_hosts`, and SSH will warn me if it ever changes.

### 2. Update the server and install Nginx

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y nginx
systemctl status nginx --no-pager      # active (running)
curl -I http://localhost               # 200 OK from inside the server
```

`curl` on `localhost` proves Nginx works **inside** the server. From outside, nothing works yet: the two firewalls block port 80.

### 3. Firewall 1: Oracle's security list

In the console: **Networking → Virtual cloud networks → navmarket-vcn → Security → Default Security List → Security rules → Add Ingress Rules**.

| Field | Value | Meaning |
| --- | --- | --- |
| Source CIDR | `0.0.0.0/0` | any address on the Internet |
| IP Protocol | TCP | HTTP runs over TCP |
| Destination Port Range | `80` | the HTTP port |

The existing rule for port 22 (SSH) stays untouched, or I would lock myself out.

### 4. Firewall 2: iptables on the server

Oracle's Ubuntu images come with their own firewall rules. The `INPUT` chain ends with a rule that **rejects** everything not allowed above it.

```bash
sudo iptables -L INPUT -n --line-numbers                                   # find the REJECT line
sudo iptables -I INPUT <N> -m state --state NEW -p tcp --dport 80 -j ACCEPT  # insert ABOVE it
sudo netfilter-persistent save                                             # keep it after a reboot
```

- `-I INPUT <N>` **inserts** the rule at position N. With `-A` (append), the rule would land **after** the REJECT and never be reached: iptables reads the rules from top to bottom and stops at the first match.
- `--state NEW -p tcp --dport 80 -j ACCEPT`: accept new TCP connections to port 80. The answers are already allowed by the `RELATED,ESTABLISHED` rule at the top.
- `netfilter-persistent save` writes the rules to `/etc/iptables/rules.v4`; without it, the rule disappears at the next reboot.

At this point, the default Nginx page opened on my phone, on mobile data, with the public IP.

### 5. The storefront lives in Git

The storefront files now live in the repository, in [`site/`](../../site/), not only on a server.

- **One source of truth**: the same files can be deployed to my local VM, to Oracle, and later to AWS.
- **History**: every change is a commit, so I can see what changed and go back.
- **Rule**: change the files in `site/`, commit, then deploy. Never edit directly on a server, or the servers and Git stop matching.

The first version of the page, from S1.3, is kept in [`S1.3-storefront-v0.html`](S1.3-storefront-v0.html).

### 6. Deploy without a half-copied site

From my workstation, in the repository:

```bash
ssh -i ~/.ssh/navmarket_vps ubuntu@$VPS_IP 'rm -rf /tmp/navmarket-site'   # remove an old upload first
scp -i ~/.ssh/navmarket_vps -r site ubuntu@$VPS_IP:/tmp/navmarket-site
```

`scp -r site X` creates `X` if it does not exist, but copies **into** it if it already exists (`X/site/...`). Removing the old upload first makes the result always the same.

On the server:

```bash
sudo rm -rf /srv/navmarket.new
sudo cp -r /tmp/navmarket-site /srv/navmarket.new
sudo chown -R root:root /srv/navmarket.new
sudo find /srv/navmarket.new -type d -exec chmod 755 {} \;    # folders: everyone can enter
sudo find /srv/navmarket.new -type f -exec chmod 644 {} \;    # files: everyone can read, root writes

sudo rm -rf /srv/navmarket.old
sudo mv /srv/navmarket /srv/navmarket.old       # keep the previous version
sudo mv /srv/navmarket.new /srv/navmarket       # the new version goes live
curl -s http://localhost/health.json            # "status": "ok", "version": "1.0.0"
```

- The new version is prepared **next to** the live one, rights included, then swapped with `mv`. A rename on the same disk is instant, so visitors never see a half-copied site. This is an **atomic swap**.
- `navmarket.old` is the **rollback**:

```bash
sudo mv /srv/navmarket /srv/navmarket.bad && sudo mv /srv/navmarket.old /srv/navmarket
```

- `health.json` is a tiny file that answers "I'm alive, version X". A script or a CI pipeline can check it after each deploy.

### 7. The Nginx site configuration

`/etc/nginx/sites-available/navmarket` (the old file was backed up first in `~/navmarket.nginx.bak`):

```nginx
server {
    listen 80;
    server_name _;                  # any name: there is only an IP for now
    root /srv/navmarket;
    index index.html;
    server_tokens off;              # "Server: nginx", without the version

    error_page 404 /404.html;       # the storefront's own 404 page

    location / {
        try_files $uri $uri/ =404;  # the file, else the folder, else 404
    }

    location /assets/ {
        expires 7d;                 # browsers keep CSS, JS and icons for 7 days
    }

    location = /health.json {
        access_log off;             # health checks don't fill the access log
    }

    location = /README.md {
        return 404;                 # the team's notes are not public
    }
}
```

```bash
sudo nginx -t                      # test before applying
sudo systemctl reload nginx        # apply without cutting visitors
```

- `location /assets/` matches every path that **starts with** `/assets/`; `location = /health.json` matches **exactly** this path.
- `server_name _`: the underscore is a name that matches nothing in particular, so this site answers any request. It becomes the domain name in session 4.
- `server_tokens off`: Nginx stops showing its exact version in headers and error pages. Before this line, the error page showed `nginx/1.18.0 (Ubuntu)`, free information for an attacker.

### 8. Test from outside

```bash
curl -sI http://$VPS_IP/ | head -5                              # 200 OK, "Server: nginx" without version
curl -s http://$VPS_IP/health.json                              # "version": "1.0.0"
curl -sI http://$VPS_IP/does-not-exist | head -1                # 404
curl -sI http://$VPS_IP/README.md | head -1                     # 404
curl -sI http://$VPS_IP/assets/css/style.css | grep -i expires  # date in 7 days
```

Then the phone, **on mobile data** (Wi-Fi off): the storefront opens from the real Internet, not from my home network.

## What I learned

- A public cloud server has **two firewalls**: the cloud's (security list) and the server's (iptables). A port must be open in both.
- iptables reads rules **from top to bottom** and stops at the first match: a new ACCEPT must be inserted **above** the final REJECT, then saved to survive a reboot.
- Testing **on mobile data** proves the service works from the real Internet, not only from my home network.
- The storefront lives in **Git** (`site/`): one source of truth for every server.
- Deploy with an **atomic swap**: prepare the new version next to the live one, rights included, rename it into place, and keep the old one for a rollback.
- `scp -r` behaves differently when the target folder already exists: clean the target first to get the same result every time.
- Nginx: `try_files`, `error_page`, `expires`, exact (`=`) and prefix `location`s, and `server_tokens off` to hide the version.
- A **403** means Nginx found the path but may not read it; a **404** means the path does not exist.

## Quick questions

**Why open port 80 in two places?**
Oracle's security list filters traffic before it reaches the server, and iptables filters it again inside the server. A packet blocked by either one never reaches Nginx.

**What does the atomic swap protect against?**
Visitors never see a half-copied site during a deploy, and the previous version stays ready for a rollback in seconds.
