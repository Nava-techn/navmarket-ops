# S1.1 — First server: `navmarket-srv01`

**Session 1 / 24 · Linux 1: using it** · Completed on 8 October 2026

## Goal

NavMarket needs its first server. Install Ubuntu Server, name it `navmarket-srv01` and bring it fully up to date.

**Done when:**

- `hostnamectl` shows `navmarket-srv01`;
- `apt list --upgradable` lists nothing left to install;
- I know whether a reboot is needed, and how I know it.

## Architecture

```
Workstation NAVATECH (Ubuntu 26.04 LTS)
│
├── virt-manager / virsh   → user interfaces
├── libvirt (libvirtd)     → manages the VMs
├── QEMU                   → emulates the virtual hardware
└── KVM (kernel module)    → runs the VM on the real CPU
        │
        └── VM navmarket-srv01 (Ubuntu Server 26.04.1 LTS)
            2 vCPU · 2 GB RAM · 20 GB disk · NAT network (virbr0, 192.168.122.0/24)
            reached from the workstation over SSH
```

I chose a **local VM** rather than a cloud server for the first labs: snapshots let me break things and roll back in seconds. The public VPS comes in lab S1.5.

## What I did

### 1. Prepare the workstation for virtualisation

```bash
lsmod | grep kvm          # KVM is already a kernel module: kvm + kvm_intel/kvm_amd
ls -l /dev/kvm            # the device file programs use to talk to KVM
sudo apt install cpu-checker qemu-kvm libvirt-daemon-system virt-manager
kvm-ok                    # the CPU supports hardware virtualisation
id                        # check that my session belongs to the libvirt group
```

KVM itself is never "installed": it ships with the Linux kernel. What I installed are the user-space layers on top of it: QEMU (virtual hardware), libvirt (VM management) and virt-manager (GUI).

### 2. Create the VM

- ISO: Ubuntu Server 26.04.1 LTS, copied to `/var/lib/libvirt/images/` (see problem 2).
- virt-manager: 2048 MB RAM, 2 vCPU, 20 GB disk, default NAT network, OS variant "Ubuntu 24.04" (see problem 3).
- Installer: hostname `navmarket-srv01`, **OpenSSH server** selected, no extra snaps.

### 3. Work over SSH, like on a real server

```bash
ssh <user>@<VM_IP>        # from the workstation; the VM gets its IP from libvirt's DHCP
```

### 4. Fix the names

The hostname and the VM name are two **independent** names:

| Name | Where it lives | How I changed it |
| --- | --- | --- |
| Hostname | inside the VM (`/etc/hostname`) | `sudo hostnamectl set-hostname navmarket-srv01` |
| Local name resolution | inside the VM (`/etc/hosts`, line `127.0.1.1`) | edited by hand with `sudo nano /etc/hosts` |
| VM name (libvirt domain) | on the workstation | `virsh domrename navmarket-svr01 navmarket-srv01` (VM shut off) |

### 5. Update the server

```bash
sudo apt update && sudo apt upgrade   # refresh the package index, then install the new versions
apt list --upgradable                 # what is still upgradable?
ls /var/run/reboot-required           # does a reboot need to happen?
sudo poweroff                         # clean shutdown before the snapshot
```

### 6. Snapshot

```bash
virsh snapshot-create-as navmarket-srv01 S1.1-clean \
  --description "Ubuntu 26.04.1 installed, hostname set, fully updated"
virsh start navmarket-srv01
```

## Proof

Full outputs: [`S1.1-proofs.txt`](S1.1-proofs.txt), collected over SSH with a Bash loop that prints each command before its output.

- `hostnamectl` → `Static hostname: navmarket-srv01`, `Operating System: Ubuntu 26.04.1 LTS`, `Virtualization: kvm`
- `/etc/hosts` → `127.0.1.1 navmarket-srv01`
- `virsh list --all` → `navmarket-srv01   running`
- `virsh snapshot-list navmarket-srv01` → `S1.1-clean`
- `apt list --upgradable` → only 2 packages left (`open-iscsi`, `libopeniscsiusr`): **phased updates**. Ubuntu releases some updates gradually to a growing share of machines, and `apt upgrade` deliberately holds them back until this machine is included. This is expected behaviour, not a failure.

## Problems and solutions

### Problem 1: virt-manager "Not connected" without `sudo`

**Symptom:** `virsh -c qemu:///system list --all` → `Failed to connect socket to '/var/run/libvirt/libvirt-sock': Permission denied`. It only worked with `sudo`.

**Diagnosis:** `sudo adduser navatech libvirt` answered *already a member*, but `id` did not list `libvirt`. Both were true: the group was in `/etc/group`, but **a process's groups are fixed when the session starts**. My graphical session was opened before the libvirt package added me to the group.

**Solution:** open a new session (log out / log in, or `newgrp libvirt` to test). Running a GUI as root with `sudo virt-manager` would have hidden the problem and is a security risk.

### Problem 2: virt-manager could not read the ISO

**Symptom:** the ISO in `~/Downloads` could not be opened by the VM.

**Diagnosis:** QEMU does not run as me but as the system user `libvirt-qemu`. `namei -l` shows the permissions of every directory on the path:

```
drwxr-x--- navatech navatech navatech      ← "others" have no x: libvirt-qemu cannot enter my home
lrwxrwxrwx navatech navatech Downloads -> /mnt/data/Downloads
```

**Solution:** copy the ISO to `/var/lib/libvirt/images/`, the standard libvirt location, instead of opening my home directory to everyone (`chmod o+x ~` would have been the wrong fix).

### Problem 3: Ubuntu 26.04 missing from the OS list

**Symptom:** virt-manager did not offer Ubuntu 26.04.

**Diagnosis:** the OS list comes from the `osinfo-db` database, which did not know this version yet. That choice only sets default virtual hardware; the ISO decides what gets installed.

**Solution:** keep the 26.04.1 ISO and choose the closest variant, Ubuntu 24.04.

### Problem 4: `/etc/hosts` and the VM name still had the old name after a reboot

**Diagnosis:** a reboot never renames anything. `hostnamectl` only writes `/etc/hostname`; `/etc/hosts` is a plain file nobody updates for you, and the VM name lives in libvirt on the workstation, outside the VM.

**Solution:** edit `/etc/hosts` by hand, then `virsh domrename` with the VM shut off. Lesson: never say "done" before checking every success criterion.

## What I learned

- KVM is part of the Linux kernel; QEMU, libvirt and virt-manager are the user-space layers on top of it.
- `apt update` refreshes the package **index**; `apt upgrade` installs the new **versions**. Always run them in that order.
- Group membership is read at login: a running session keeps its old groups.
- Services often run as their own system user (`libvirt-qemu`): permissions must be checked for **that** user. `namei -l` is the tool for any "Permission denied" on a path.
- The hostname, `/etc/hosts` and the hypervisor's VM name are three separate things.
- Phased updates explain why some packages stay "upgradable".
- `sudo poweroff` stops services cleanly and flushes data to disk; "force off" is like pulling the power cable.
- `>` creates or overwrites a file, `>>` appends to it; `2>&1` also captures error messages.
- Working over SSH from my workstation is the normal way to run a server; a snapshot is a cheap safety net before every lab.
