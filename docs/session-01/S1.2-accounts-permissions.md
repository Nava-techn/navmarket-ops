# S1.2 — Accounts alice, bob, chloe and permissions on `/srv/navmarket`

**Session 1 / 24 · Linux 1: using it** · Completed on 9 October 2026

## Goal

NavMarket is hiring. Three people need an account on `navmarket-srv01` and access to the website files:

| Account | Role | Rights on `/srv/navmarket` |
| --- | --- | --- |
| alice | Web developer | read + write |
| bob | Web developer | read + write |
| chloe | Intern, reviews the site | read only |

**Done when:**

1. alice creates a file in `/srv/navmarket`, and bob can modify it without any `chmod`;
2. chloe can read that file, but gets `Permission denied` when she tries to write;
3. every permission can be explained with `ls -l` and `namei -l`.

## Design

| Decision | Choice | Why |
| --- | --- | --- |
| Location | `/srv/navmarket` | The FHS defines `/srv` for data **served** by the machine (web, FTP). Website files are not personal data, so they don't belong in a `/home`. |
| Owner | `root` | A shared directory should not belong to one person: if alice leaves and her account is deleted, nothing breaks. |
| Group | `webteamgrp` (alice, bob) | Rights are given to a **group**, not to each person: when the team changes, I change one group, not every file. |
| Mode | `2775` (`drwxrwsr-x`) | see below |

**The mode `2775`, digit by digit:**

| Digit | Value | Rights | For whom |
| --- | --- | --- | --- |
| 1st | 2 | setgid | new files inherit the directory's group |
| 2nd | 7 | `rwx` | owner `root` |
| 3rd | 7 | `rwx` | group `webteamgrp` |
| 4th | 5 | `r-x` | others, which includes chloe |

On a **directory**, `r` lets you list the names, `w` lets you create or delete files inside, and `x` lets you enter it. chloe needs `r-x` (5), not `r--` (4): without `x` she could see the file names but not open them.

## What I did

```bash
sudo adduser alice                    # same for bob and chloe
sudo addgroup webteamgrp
sudo adduser alice webteamgrp         # same for bob; chloe stays outside the group
sudo mkdir /srv/navmarket             # /srv belongs to root, so sudo is required
sudo chown root:webteamgrp /srv/navmarket
sudo chmod 2775 /srv/navmarket
ls -ld /srv/navmarket                 # drwxrwsr-x root webteamgrp: the "s" is setgid
```

## Proof

Full outputs: [`S1.2-proofs.txt`](S1.2-proofs.txt), collected on the server with a Bash loop that prints each command before its output.

- `getent group webteamgrp` → `alice,bob`; `id chloe` → not in `webteamgrp`
- `ls -ld /srv/navmarket` → `drwxrwsr-x root webteamgrp`
- `ls -l /srv/navmarket` → `-rw-rw-r-- alice webteamgrp index.html`: created by alice, group inherited from the directory, writable by the group
- `namei -l /srv/navmarket/index.html` → every directory on the path can be entered by others
- `sudo -u chloe touch /srv/navmarket/test-chloe` → `Permission denied`

## Why bob can edit alice's file: setgid + umask

Two things must be true at the same time:

1. **setgid on the directory**: without it, `index.html` would belong to alice's own group `alice`, and bob, who is not in it, could not write.
2. **umask `0002`**: new files start at `666`, and the umask removes rights, so `666 − 002 = 664` (`rw-rw-r--`). With the common `0022`, the file would be `644` and bob would be refused despite setgid. Ubuntu uses `0002` safely because of **user private groups**: every user has their own group with the same name (`alice:alice`, `bob:bob`…).

## Problems and solutions

### Problem 1: the file was not where I expected

**Symptom:** after `touch /srv/navmarket/ index.html`, `ls -l /srv/navmarket/index.html` answered `No such file or directory`.

**Cause:** the **space** split the command into two arguments. `touch` updated the date of the directory `/srv/navmarket/`, then created `index.html` in the **current directory**, alice's home. A later `rm /srv/navmarket/ index.html` run as alice deleted that stray file.

**Lesson:** one extra space changes the meaning of a command. With `rm -rf`, `rm -rf /tmp/old` deletes one folder, while `rm -rf / tmp/old` targets the whole system. Always reread a destructive command before pressing Enter.

### Problem 2: `tee -a` "froze"

**Cause:** `tee -a FILE` copies **standard input** to FILE. Without a file name and without input, it simply waits for keyboard input. `Ctrl+D` ends the input, `Ctrl+C` interrupts.

**Note:** `sudo -u bob echo "text" >> file` would not test bob's rights, because the redirection `>>` is handled by **my** shell before `sudo` runs. The correct form is `echo "text" | sudo -u bob tee -a file`.

### Problem 3: nested sessions with `su`

**Cause:** running `su - chloe` from bob's session opens a session inside another one (valdes → bob → chloe). `whoami` tells who I am, `exit` goes back one level. An administrator does not know the users' passwords anyway: `sudo -u <user> <command>` only needs the admin's own password, which is how the proofs were collected.

## What I learned

- `/srv` is the FHS location for data served by the machine.
- Rights go to **groups**; a shared directory is owned by `root` and a team group.
- `rwx` means something different on a directory: `x` is the right to enter.
- The **setgid** bit on a directory makes new files inherit its group.
- The **umask** decides the rights of new files; `0002` + user private groups make team directories work.
- Test permissions as the real user with `sudo -u`, and keep the failing test as proof.
- Spaces split arguments: reread every command, especially `rm`.
- Limit of this design: "others" includes **every** user on the server. Giving read access to chloe only would need ACLs (`setfacl`), a possible improvement.
