# S2.6 - Top 10 IPs attacking my VPS over SSH

**Session 2 / 24 · Linux 2: administering** · Completed on 30 October 2026

## Goal

From the SSH logs of `navmarket-vps01`, measure the attacks: how many failed logins, from how many IPs, the top 10 attackers and the user names they try.

**Done when:** one script gives these numbers from `auth.log` (current + rotated), and they show that S2.1 blocks everything.

## What I did

[`scripts/session-02/s2.6-ssh-attackers.sh`](../../scripts/session-02/s2.6-ssh-attackers.sh) (run with `sudo`):

```bash
zcat -f $(ls -tr /var/log/auth.log*) \
  | grep -E 'Invalid user|Failed (password|publickey)|\[preauth\]' \
  | grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' | sort | uniq -c | sort -rn | head -10
```

- `grep -E '...'`: keeps failed or aborted logins (unknown user, refused key, connection closed before login).
- `grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}'`: `-o` prints only the match, here an IPv4 address.
- `ls -tr`: oldest file first, so the period reads in time order.
- User names: `grep -oE 'Invalid user [^ ]+' | awk '{print $3}' | sort | uniq -c | sort -rn`.

## Proof

Full outputs: [`S2.6-proofs.txt`](S2.6-proofs.txt). IPs masked as `a.b.x.x`.

- **56,054** failed or aborted login lines from **1,531** different IPs, in about 2 weeks (~4,000 a day)
- top attacker: 3,793 lines from a single IP
- top user names tried: `admin` (2,484), `user`, `debian`, `test`, `administrator`, `oracle`, `postgres`, `ftpuser`, `git`
- every attempt failed: password logins are disabled ([S2.1](S2.1-ssh-keys-only.md))

## Problems and solutions

### The period was printed backwards

**Symptom:** `Period: Oct 24 -> Oct 16`. **Cause:** `auth.log*` expands in name order (`auth.log`, `auth.log.1`, `auth.log.2.gz`), newest first. **Solution:** `zcat -f $(ls -tr /var/log/auth.log*)` reads the oldest file first.

## What I learned

- An SSH port on the Internet is attacked within minutes, by thousands of IPs, with common user names: keys-only login is the first protection.
- `auth.log` records every attempt; `[preauth]` lines are connections closed before any successful login.
- Next steps to reduce the noise: `fail2ban` (bans an IP after N failures, planned in session 4) and Oracle's security list.

## Quick questions

**Why are the attackers trying `admin`, `oracle` or `postgres`?**
They try default or common account names, hoping for a weak password; with keys only, the name does not matter.
