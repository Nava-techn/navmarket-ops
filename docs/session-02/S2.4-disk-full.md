# S2.4 - Add a disk, mount it, fill it, diagnose it

**Session 2 / 24 · Linux 2: administering** · Completed on 28 October 2026

## Goal

Add a data disk to `navmarket-srv01`, mount it permanently, fill it, and diagnose a full disk, including a deleted file that still takes space.

**Done when:**

1. a new disk is partitioned, formatted and mounted from `/etc/fstab`;
2. I can show it full and find what fills it;
3. I can explain and fix "`df` says full, `du` says empty".

## What I did

### 1. A 1 GB virtual disk, plugged in live (on the workstation)

```bash
sudo qemu-img create -f qcow2 /var/lib/libvirt/images/navmarket-srv01-data.qcow2 1G
virsh -c qemu:///system attach-disk navmarket-srv01 /var/lib/libvirt/images/navmarket-srv01-data.qcow2 vdb \
  --driver qemu --subdriver qcow2 --targetbus virtio --persistent --live
```

`--live`: plugged in now (hot-plug); `--persistent`: still there after a reboot.

### 2. Partition, format, mount for good (on srv01)

```bash
sudo parted -s /dev/vdb mklabel gpt mkpart navdata ext4 1MiB 100%   # GPT table, one partition: vdb1
sudo mkfs.ext4 -L navdata /dev/vdb1                                  # ext4 file system with a label
sudo mkdir -p /mnt/navdata
echo "UUID=<uuid of vdb1> /mnt/navdata ext4 defaults,nofail 0 2" | sudo tee -a /etc/fstab
sudo systemctl daemon-reload && sudo mount -a                        # an fstab error shows now, not at reboot
```

- **UUID**, not `/dev/vdb1`: device names can change between boots, the UUID does not (`blkid`).
- **`nofail`**: if the disk is missing, the server still boots.

### 3. Fill it, diagnose it

```bash
sudo dd if=/dev/zero of=/mnt/navdata/fill.bin bs=1M      # until "No space left on device"
df -h /mnt/navdata                                       # file system view: 100%
sudo du -ah /mnt/navdata | sort -h | tail -3             # file view: fill.bin takes the space
```

### 4. The trap: a deleted file still open

```bash
sleep 300 < /mnt/navdata/fill.bin &     # a process keeps the file open
sudo rm /mnt/navdata/fill.bin           # du: empty, df: still 100%
sudo lsof +L1 /mnt/navdata              # deleted but open files (link count 0)
kill <pid>                              # the space is freed only now
```

A file's space is freed when its **last name** is removed **and** the **last process** closes it. In real life: a log file deleted while the service still writes to it.

## What I learned

- Disk chain: disk → partition table (GPT) → partition → file system → mount point → fstab.
- `lsblk` shows disks and mounts; `blkid` gives UUIDs; `findmnt` shows where something is mounted.
- `mount -a` tests fstab safely before a reboot; `nofail` keeps a missing disk from blocking the boot.
- `df` counts blocks used by the file system, `du` adds up the files it can see: when they disagree, look for deleted open files with `lsof +L1`.
- Fix a "full disk" by stopping (or restarting) the process holding the file, or by emptying a file with `truncate -s 0` instead of deleting it.

## Quick questions

**`df` says 100% but `du` finds almost nothing. What do you check?**
Deleted files still held open by a process: `lsof +L1`. Restart that process to free the space.
